## The slice, decided here

- **The runbook gets its own file** in `docs/guidelines/cloudflare-switch.md` (front matter `description`), linked from `operations.md` § Deployments and from the shape. It is a one-off procedure with its own rollback, and folding it into `operations.md` would bury the day-to-day runbook. `docs:inventory` reads only `docs/list-*.md`, so a new guideline file cannot break it.
- **Workers Paid ($5/month on the Multimage account) is the recommendation**; the runbook gives both plans with the numbers. Requests are not the problem: 202,943 Vercel requests in 30 days ≈ 6.8k/day; with two billed requests per view (gateway + Backend) plus static assets that is at most ≈ 14k/day, against 100k/day on Free. CPU is the problem: a cache miss renders in 26 ms median and up to 100 ms on `/autori`, against Free's 10 ms. Every deploy, purge, draft view and `/api` call is a miss. Paid includes 30M CPU-ms; 140k renders × 26 ms ≈ 3.6M even with no cache at all. The Worker is 2.3 MiB gzip, against Free's 3 MiB and Paid's 10 MiB.
- **Custom domains as code**: on switch day `routes` with `custom_domain: true` for `www.multimage.org` and `multimage.org` goes into `wrangler.jsonc`, so a later `wrangler deploy` cannot drift from the dashboard. It is not added now: the zone is still in the personal account, so the deploy would fail. Order: `npm run build:cf` first, then delete the two Vercel records, then `npx wrangler deploy` (no rebuild), which keeps the gap short. A Custom Domain cannot be created while a DNS record exists for its hostname.
- **Apex → www**: a Cloudflare Redirect Rule, 301 with the path kept. Today Vercel answers `307 https://www.multimage.org/libri` for `https://multimage.org/libri` (checked 2026-11-21). Without the rule, the apex would serve a duplicate site.
- **Full purge = a new Worker version**: the cache is partitioned by version (`cfdocs/cache_purge.md` § Version-specific purging), and the app has no purge-everything endpoint. So `npm run deploy:cf` runs after the `cda_cache_tags` webhook exists. That closes the window in which a publish would be missed.
- **Webhook 33942 is disabled, not deleted**, at the same step as the new webhook. After the DNS change its URL reaches the Worker, which has no `BYPASS_TOKEN`: `/api/revalidate` would fail and retry, and both endpoints would reindex Site Search. Deletion goes into the Vercel follow-up.
- **seo-analysis needs a CMA token on the trial Worker** to reach its self-fetch. T1 copies `DATOCMS_CMA_TOKEN` from the local `.env` through a `dotenv` child shell: the value is never printed or written, the same form as `caching.md` (b)/(c). It deletes the secret at the end. `SITE_SEARCH_BUILD_TRIGGER_ID` stays unset, so no reindex can fire. If `.env` has no such token, the self-fetch check moves to runbook step 9.
- **Tests (essential)**: no file. T2 touches `src/pages/api/`, but the `Backend` binding exists only on the deployed Worker and there is no test runner: the test is T1 step 5 re-run on the redeploy.
